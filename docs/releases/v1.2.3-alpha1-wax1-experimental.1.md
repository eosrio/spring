# Spring WAX profile v1.2.3-alpha1-wax1-experimental.1

> **Experimental prerelease — WAX Testnet and local development only.**
> Do not deploy this build to WAX Mainnet producers or treat the consensus-module
> API as stable. This release exists to gather independent replay, validation,
> packaging, and operational evidence from the Antelope community.

## Why this release exists

WAX has historically maintained a full node fork to preserve a small amount of
chain-specific compatibility code. Comparing the current WAX fork with its
Spring Community Edition baseline found one surviving WAX-specific consensus
extension: the `env.verify_rsa_sha256_sig` WASM intrinsic used by WAX ORNG.

This experiment moves that behavior into a narrowly owned compile-time consensus
module in the EOSRIO Spring 1.2.3 maintenance line. The shared Spring codebase can
then receive fixes and runtime improvements without requiring WAX maintainers to
continually merge an entire fork.

This is intentionally a compile-time consensus module, not an appbase plugin or
a dynamically loaded shared library. Code executed during transaction validation
must be present before WASM runtime and EOS-VM-OC compiler initialization and must
remain identical on every validating node.

## Release-profile model

The same source commit produces separately named and auditable release profiles:

| Profile | Package | Consensus modules |
| --- | --- | --- |
| `vanilla@1` | `antelope-spring` | none |
| `wax@1` | `antelope-spring-wax` | `wax@1.0.3wax01` |

The WAX profile is not bound to a production chain ID. Developers can use it to
bootstrap arbitrary local WAX-compatible chains. Profile selection determines
the intrinsic set for a new genesis; existing snapshots retain their on-chain
intrinsic whitelist.

The WAX and vanilla packages conflict at the package-manager level because they
install the same node tools. This is deliberate protection against silently
overwriting one consensus profile with another.

## Included WAX behavior

The WAX module preserves the observable behavior of the current WAX fork's
`verify_rsa_sha256_sig` implementation:

- SHA-256 message hashing;
- PKCS#1 v1.5 SHA-256 encoded-message comparison;
- hexadecimal signature, public exponent, and modulus inputs;
- the existing validation and failure behavior;
- registration in EOS-VM, EOS-VM-JIT, and EOS-VM-OC;
- availability in the WAX profile's genesis intrinsic set.

The module does not contain WAX branding, peers, chain IDs, token precision,
governance, resource economics, or system-contract logic. Those are packaging,
configuration, on-chain state, or ordinary WASM contracts and do not require a
node consensus fork.

## Auditable build identity

The profile definition, module descriptor, implementation source, intrinsic
names, and versions are included in a generated manifest. Their SHA-256 hashes
are combined into a profile-wide manifest hash, which is also mixed into the
EOS-VM-OC cache identifier.

Every node exposes this identity through startup logs, `nodeos --full-version`,
and `/v1/chain/get_info`:

```json
{
  "server_consensus_profile": "wax@1",
  "server_consensus_module_manifest": "wax@1.0.3wax01=verify_rsa_sha256_sig#...",
  "server_consensus_manifest_hash": "..."
}
```

The full version has the following shape:

```text
v1.2.3-alpha1-<git-commit>+consensus.wax.1.<manifest-prefix>
```

Please include the full version and manifest hash in every test report.

## Validation completed before publication

### Differential compatibility

- The original WAX fork's six RSA tests pass unchanged under EOS-VM and
  EOS-VM-JIT: 67 of 67 assertions in each runtime.
- The module compatibility suite passes under EOS-VM, EOS-VM-JIT, and
  EOS-VM-OC.
- The vanilla profile rejects the WAX intrinsic import, demonstrating that WAX
  behavior is absent from the standard release.
- Invalid lengths, invalid hexadecimal inputs, minimal messages, malformed
  parameters, corrupted signatures, and valid signatures are covered.

### Real WAX production vector

The deterministic suite contains the exact cryptographic inputs from WAX Testnet
block `419439156`, transaction
`f541307e62ee07e54879ba9fd31b5032e594edb5e0af12ad2d1553f0a163c174`,
action `orng.wax::setrand`, request `3641`. The message reconstruction and
4096-bit RSA signature verify successfully under all three Spring runtimes.

### WAX Testnet operation

- Restored a WAX Testnet v6 snapshot at block `419754590` with the packaged
  archive binary, rather than a developer-tree build.
- Synchronized and validated new blocks on chain ID
  `f16b1833c747c43682f4386fca9cbb327929334a762755ebec17f6f23c9b8a12`.
- Tested clean restarts without reapplying the snapshot, including a restart
  after the live ORNG result described below became irreversible.
- Ran with EOS-VM-JIT and `eos-vm-oc-enable=all`.
- Maintained four independent peer connections with no node errors after the
  profile-aware restart.
- Queried the live `orng.wax` ABI and contract state through the candidate node.
  The deployed contract exposes `requestrand`, `setrand`, and `randnotify`, and
  its three configured Testnet oracles were active and had zero strikes at the
  time of testing.

### Packaged artifact checks

- Built the WAX profile in the pinned Clang 18 reproducible-build container and
  verified both release files against `SHA256SUMS.txt`.
- Ran the portable archive's `nodeos` and checked its full version, profile,
  module manifest, and manifest hash before connecting it to WAX Testnet.
- Installed the `.deb` in clean Ubuntu 22.04 and Ubuntu 24.04 containers and
  ran the packaged `nodeos --full-version` smoke check in both.
- Confirmed that the `.deb` is named `antelope-spring-wax`, conflicts with the
  vanilla `antelope-spring` package, and declares only its runtime library
  dependencies.

## What the community should test

1. Restore recent WAX Testnet snapshots and report synchronization behavior.
2. Test EOS-VM-JIT and EOS-VM-OC independently, including restarts and OC cache
   recreation.
3. Create and restore snapshots produced by this release.
4. Bootstrap local chains with the WAX profile and arbitrary chain IDs, then
   deploy WAX applications that import the RSA intrinsic.
5. Independently repeat a real `orng.wax` request on WAX Testnet and report the
   request, oracle-response, and irreversible block identifiers.
6. Run mixed producer/validator topologies where every node uses the same WAX
   profile, but runtime choices differ.
7. Measure CPU and memory behavior for realistic and adversarial RSA parameters.
8. Test the `.deb` and archive on the operating systems used by community test
   nodes.

Reports should include the operating system, CPU architecture, runtime and OC
settings, snapshot or replay starting block, observed head, full node version,
manifest hash, and relevant logs.

### Live ORNG validation

The [`wax-orng` repository](https://github.com/worldwide-asset-exchange/wax-orng)
documents the current contract flow and includes a dice-game receiver example.
The source reviewed for this release was commit
[`7b84fede`](https://github.com/worldwide-asset-exchange/wax-orng/tree/7b84fede311db5a2f4d26bfb441ba5bebf751f9f).
Its local JavaScript tests run the contract in Vert; they are valuable contract
tests but do not execute this node's native intrinsic.

The repository's
[receiver example](https://github.com/worldwide-asset-exchange/wax-orng/tree/7b84fede311db5a2f4d26bfb441ba5bebf751f9f/example)
was compiled with its documented WAX development image and deployed to the
disposable WAX Testnet account `waxspringexp`. The account was granted only its
own `eosio.code` authorization. No signing key is included in this release.

The complete live path was observed through the packaged node:

| Step | Evidence |
| --- | --- |
| `waxspringexp::rolldie` / inline `orng.wax::requestrand` | transaction `d6302a5c4f7b1f168375ca34ea283182ad2973458cd6fd13eab9cc107bfa4725`, association ID `1`, block `419805998` |
| oracle `orng.wax::setrand` | oracle `rng3.wax`, transaction `4c0b3d4d987e5e696f9f9efaf035886216264e61a8fad5b25c4b5df679871207`, block `419806003` |
| `orng.wax::randnotify` receiver result | roll `1`, die result `3`, resolution time `3` seconds; pending request and pending roll removed |
| irreversibility | response block `419806003` confirmed irreversible at LIB `419806034` |
| restart readback | result remained present after a clean packaged-node restart; profile `wax@1` and manifest hash `18f30c2ef041849ce691cd2a9f316d06abe5c58bf0fbd5b3bf6be2477a1d1aca` unchanged |

The oracle's `setrand` action is the consensus-critical step: accepting that
transaction executes `verify_rsa_sha256_sig` on the validating node. The
request used the contract's guaranteed free allocation, reducing its credits
from 10 to 9, so no Testnet token transfer or ORNG deposit was necessary.

## Known limitations and safety notes

- A full genesis-to-head WAX replay has not yet been completed. The available
  snapshot begins after the historical ORNG vector, so that historical
  transaction was validated as an exact deterministic vector rather than
  replayed from genesis. A separate post-snapshot live ORNG response was
  validated end to end as documented above.
- Spring's chainbase database environment signature includes compiler details.
  An existing database created by the GCC 13 developer build correctly refused
  to open under the Clang 18 release package. When changing compiler or other
  chainbase environment parameters, restore a snapshot or replay into a fresh
  data directory instead of copying the existing `state` directory. This is an
  operational migration requirement, not a WAX consensus-profile mismatch.
- The WAX implementation performs multiprecision modular exponentiation over
  contract-controlled input without a dedicated deterministic work limit. This
  preserves deployed WAX behavior but requires focused resource-exhaustion review
  before production adoption.
- The consensus-module API, manifest schema, profile versioning policy, and
  `get_info` metadata fields are experimental and may change before stabilization.
- Do not use the WAX profile to bootstrap a vanilla network. It intentionally
  includes the RSA intrinsic in a new chain's genesis set, and nodes built without
  that profile would reject contracts that import it.
- Snapshot synchronization demonstrates compatibility from the snapshot forward;
  it does not replace a complete historical replay and long-duration producer
  soak test.
- This release has not been audited as a production consensus implementation.

## Source and feedback

The WAX module and profile are maintained in the central `eosrio/spring` source
tree so changes can be reviewed atomically with the consensus API and runtimes.
Please report results and failures through the repository issue tracker. Do not
include private keys, signing-provider secrets, or private peer credentials in
logs.

The experiment builds on the historical WAX implementation and test vectors from
`worldwide-asset-exchange/wax-blockchain`, the WAX ORNG contract, and the EOSRIO
Spring 1.2.3 maintenance line.
